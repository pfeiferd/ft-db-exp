# The human saliva runs of the first Genestrip paper (its Table "errorsviral"): DNA sequencing of
# saliva from different donors, downloaded from the SRA. They are the real data without ground truth
# that `cv', the complete viral database, is applied to, exactly as in that paper -- and, since saliva
# is a streptococcal habitat, that `strepto' is applied to as well, on the very same files.
#
# Unlike ticks_real.txt this map holds no URLs, because these runs are paired: each arrives as two
# files that have to be read under one key, and the URLs have to be resolved per accession. That is
# what the fetch script does, so the files are downloaded separately:
#
#   sh ./bin/fetch_saliva.sh                  # every run below -- see that script's volume warning
#   sh ./bin/fetch_saliva.sh SRR5571991       # a single run
#
# It fetches the gzipped fastq files from the ENA over HTTPS, resumably and md5-verified. Going
# through sra-tools instead (METHOD=sra) does not work at these sizes on an ordinary disk: turning
# the .sra archive into fastq writes the reads out uncompressed first, so SRR5571991 needs some
# 615 GB transiently to yield 139 GB, and fasterq-dump aborts with "disk-limit exeeded!". The
# script's header explains this in full.
#
# and this map refers to the result by name, resolved against data/fastq as usual. The names are the
# accessions, as in the original genestrip-db-exp project, so runs already fetched there are reused.
#
# All five runs of that paper's Table "errorsviral", in its own order. Its project fetched only the
# three SRR runs through sra-tools and left ERR1395613 (#2) and ERR1395610 (#4) commented out, and
# this map followed that choice for a while -- wrongly: the paper reports measurements for all five,
# in results/viral_human_virus_errors_gs_ku_comp.csv and results/viral_saliva_rel_accuracy.csv, so
# omitting two of them would compare against less data than the study this one builds upon.
#
# ONLY THE FIRST MATE OF EACH RUN IS LISTED, so that these numbers can be held against the first
# paper's. Genestrip has no notion of a pair: it classifies every record on its own, so a second
# mate is simply a second read, and reading both doubles the reads of a run rather than pairing
# them. That paper's Table "analysisperf" reports 824,743,085 reads per file at 101 bp -- exactly
# the mean of the five runs' spot counts at one mate's length, i.e. it analysed one mate per run.
# Reading both here would double every read count, wall time and |R'_g| against it and make the two
# studies incomparable for no gain in evidence: the second mate of a fragment comes from the same
# organism as the first and adds no independent observation of what is in the sample.
#
# The second mates stay on disk and are listed commented out, so taking them back in is one edit.
#
#   key         #    read pairs      bases     gzipped   read length
#   SRR5571985  1    812,085,208     164 Gbp   112 GB    101 bp
#   ERR1395613  2    900,709,176     180 Gbp   171 GB    100 bp
#   SRR5571991  3    980,879,835     198 Gbp   139 GB    101 bp   <- reported in detail by that paper
#   ERR1395610  4    824,479,570     165 Gbp   154 GB    100 bp
#   SRR5571990  5    605,561,636     122 Gbp    78 GB    101 bp
#                                              -------
#                                              654 GB
#
# Sizes and read lengths as the ENA reports them; all five are Illumina HiSeq 2000. The 100 bp of
# the two ERR runs against the 101 bp the "saliva-like" simulated set reproduces is a one-base
# difference and does not disturb the calibration of Section "Estimating the gain without ground
# truth", but it is worth knowing before the two sets are held against each other.
#
# ALL FIVE RUNS, as in the first paper. The two ERR ones were left out on 2026-08-22 for disk and
# wall time -- at 171 and 154 GB for both mates they are the largest of the set -- and are back
# because only the first mate of each run is fetched and read: 326 GB for all five against 654.
#
# They are not equally informative. SRR5571990 leaves 734 of its 22 million classified reads at a
# genus, 0.003 %, against 0.13 % for SRR5571985 and 0.08 % for SRR5571991, and over half of those sit
# under one genus -- so its precision rests on very little and should be read with |R'_g| beside it,
# which is why the paper's table prints that column.
#
# Scoring even the three in one call is a multi-day proposition. To take them one at a time, copy
# the line of one run into a map of its own -- perf_scenarios.sh does exactly that per key and
# removes the file again, which is why no single-run map is kept here.
#
